# Elixir / Phoenix / OTP — domain mental model

A code-validated mental model of how this stack is built and where its load-bearing seams
live. Validate every claim against the cited `module:line` before relying on it; the
self-improve job refreshes this from the actual tree after each build.

## Architecture seams
- Contexts own ALL `Repo`/`Ecto.Query` access; LiveViews / controllers / OTP processes call
  context functions, never the Repo directly (`RepoBuilder.Schema`, the `*.ex` context modules).
- One supervised GenServer per live unit of work; `:temporary` children are not auto-restarted
  (`RepoBuilder.Session.Server`, `RepoBuilder.Orchestrator.Server`).
- Liveness is layered: a soft quiescence timer demotes a quiet worker to `:idle`, a
  `Process.monitor` push detects death instantly, and a periodic reaper is the restart backstop.

## Typed-Elixir guardrails
- `@spec` on every public function; precise types over `any()`/`map()`; tagged tuples over
  raising (BUILD_PROMPT.md §3).
- TypedStruct + `@enforce_keys` for domain data; closed `Ecto.Enum`s for closed sets, validated
  `:string` for open identity (harness/provider).

## Drive-loop facts
- The orchestrator reconciles a durable Task Ledger + per-turn Progress Ledger; the Driver
  drives idle orchestrators with an active goal toward DONE (stall → replan → escalate).
- Verify "done" against the actual tree with `inspect_repo`, never a worker's self-report.
