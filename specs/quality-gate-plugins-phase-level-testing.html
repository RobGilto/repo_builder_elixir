Purpose

Give repo_builder a rigorous, per-stack testing discipline that the orchestrator enforces at the phase level. Today the platform's own Elixir gate (compile --warnings-as-errors · format · credo --strict · test · dialyzer) is a strong agent feedback loop, but that discipline is hardwired to this repo. When repo_builder builds a Rust, Go, Python, TypeScript, or Ruby repo, there is no equivalent single "am I done?" oracle for the worker to satisfy. This plan makes the green gate a plugin object: a stack-aware, ordered set of quality stages the orchestrator runs during each workstream phase's :test stage, looping fix-workers until the gate is green.

Problem

LLM-written code satisfices. Three failure modes matter for autonomous, phased building:

  • Permitted warnings ship. Without a binary red/green gate, a model treats a warning as "good enough". The platform already knows this — elixirc_options: [warnings_as_errors: true] and mix test --warnings-as-errors are in CI — but that rule lives only in this repo, not in the repos the orchestrator builds.
  • Hallucinated APIs slip past tests. A static type stage (Dialyzer here; tsc --noEmit, mypy/pyright/ty, cargo check, Sorbet elsewhere) is the cheapest verifier — it catches invented methods and contract drift without executing anything. Most stacks the orchestrator targets have a type gate available, but nothing wires it into the phase loop.
  • Vacuous tests pass. Models are exceptionally good at writing tests that hit coverage lines while asserting nothing. A line-coverage gate actively rewards this. The antidote — mutation testing — has no place to live in the current phase machine.

Structurally, the workstream :test stage (lib/repo_builder/orchestrator/workstream_phase.ex) is a single "dispatch /test, record passed/failed" step. It has no notion of an ordered, strict, per-stack gate, and no seam for a plugin to supply one.

Solution

Add a Quality-Gate subsystem, delivered through the existing agentic plugin system, with four moving parts that all reuse seams already in the codebase:

  1. A new closed contribution kind :quality_gate (RepoBuilder.Plugins.Contribution). Per the plugin doctrine — "open plugin id, CLOSED set of kinds; adding a kind is a deliberate core edit because it means a new extension point" — a gate is a genuinely new extension point, so it earns a kind rather than overloading :capability.
  2. A gate descriptor + domain type (RepoBuilder.Plugins.QualityGate): a JSON file declaring an ordered list of stages for a stack, each stage a capability-tokenized command with a strict flag, a cadence (per_phase | pre_merge), and a diagnostic format. Validated wire→domain via TypeCheck, exactly like Manifest/Contribution.
  3. A resolver + runner (GateResolver + Orchestrator.GateRunner): resolve the active gate for a project's stack across a precedence chain (active plugin → builtin stack default under priv/quality_gates/ → generic), fill capability tokens with the same {{TEST_COMMAND}}… machinery the command Resolver already uses, run each per_phase stage in order, and parse file:line:rule diagnostics so the fix-worker can self-correct.
  4. Orchestrator integration: a run_quality_gate tool the orchestrator calls during the :test stage. Any red stage → dispatch a fix worker → re-run → loop, bounded by the existing @stall_limit. pre_merge stages (mutation, property depth) run once at close_workstream. Gate outcomes persist in the phase's stages JSONB and surface on the Workstreams console panel.

Stacks ship as plugins in plugin_library/quality-gates-<stack>/ (elixir, rust, go, python, ts, ruby), each pairing a quality_gate descriptor with a context_fragment/skill that teaches the worker the five-stage discipline plus mutation/property testing. Builtin defaults under priv/ mean the gate works with zero plugins installed (mirroring stack packs → generic).

Questionables

New :quality_gate contribution kind vs. reusing :capability?

Chosen: new kind. The plugin doctrine is "open plugin id, CLOSED kind set; a new kind is a deliberate core edit because it marks a new extension point." A gate is a genuinely new extension point (ordered, strict, cadence-bearing, diagnostic-parsed) — not just a capability default value. Overloading :capability (which is a flat JSON of stack markers/defaults) would blur that contract and make resolution ambiguous. The one-line edit to @kinds is exactly the intended "deliberate core edit."

Which Python type checker is the default gate stage?

Chosen: Pyright (or Pyrefly) now; watch ty. Verified 2026-07: Astral's ty is in beta with a stable release targeted for 2026 and ~53% conformance / no plugins; Meta's Pyrefly hit 1.0 (~58%, auto-migrates mypy/pyright config); Pyright leads correctness (~98% conformance). For spec-driven work where the type stage is the primary hallucination catcher, default to Pyright/Pyrefly and make it swappable via the descriptor's capability token, so a project can adopt the Ruff+uv+ty single-vendor stack once it stabilizes without a core change.

Should the gate enforce a typed system, optionally, per stack?

Yes — a first-class, optional typed_enforcement policy, default :strict. A type checker passing is not a typed system enforced: plain JS clears tsc trivially, un-annotated Python clears pyright in non-strict mode, Ruby without Sorbet has nothing to check. So the capability typed_enforcement :: :off | :standard | :strict selects a type-stage variant in GateResolver: :strict (default) runs the strict checker (pyright --strict / mypy --strict / strict-tsconfig / Sorbet typed: strict) and an annotation-coverage sub-stage — the generalization of this platform's own hard Credo "every public fn has an @spec" gate ([[typed-coding-standard]]). :standard runs the plain checker; :off skips it for fast/dynamic prototypes. Default :strict because in spec-driven work the types are the machine-checkable spec, and it makes repo_builder impose on the repos it builds exactly the discipline it imposes on itself. No new contribution kind — one capability field + a resolver variant selector, reusing the Stage.strict flag.

Cadence: should mutation/property gates run per phase?

Chosen: pre_merge (workstream close), not per-phase. Mutation testing is slow (it re-runs the suite per mutant). Running it per edit would poison the fast feedback loop. The descriptor's cadence field lets format/lint/type/test run per_phase (fast, every phase) while mutation/property depth run once at close_workstream — the "nightly/pre-merge" tier. Verified against 2026 mutation-testing guidance (Stryker/cargo-mutants CI threshold patterns).

Where does the gate actually execute — orchestrator BEAM or worker sandbox?

Chosen: worker sandbox via the tool handler. The orchestrator BEAM must not shell out into target-repo toolchains (wrong cwd, no isolation, blocks the scheduler). GateRunner produces the ordered, token-filled command plan; the run_quality_gate tool has the phase's worker execute it in its own working directory and returns the structured result. This reuses the existing worker-execution + session-runtime seam.

Diagnostic parsing: generic file:line or per-stack parsers?

Chosen: generic file:line now, per-stack later. A diagnostic: :file_line | :summary | :none flag per stage covers the common case (nearly all these tools emit path:line[:col]). Structured JSON parsers (e.g. biome ci --reporter=json, cargo clippy --message-format=json) are a follow-on refinement per descriptor, not a v1 blocker.

Does this duplicate the platform's own CI gate?

No — it generalizes it. The Elixir builtin descriptor is the platform's own five-command gate, made data-driven. repo_builder's own CI stays as-is; the gate subsystem is what the orchestrator applies to the repos it builds. The Elixir descriptor doubles as the reference implementation and a self-test.

Notes

The five transferable properties (why the Elixir gate works as an agent loop)

These are the design invariants every stack descriptor must preserve — the reason the gate is a feedback loop, not just a command list:

  • One command, one exit code. The gate is the worker's "am I done?" oracle. Each stack needs a single wrapper.
  • No-warnings tier. --warnings-as-errors everywhere — the single most important trait for LLM-written code. A permitted warning is a warning that ships. Binary red/green.
  • Static types as the cheapest verifier. Type stages catch hallucinated APIs without executing anything. In spec-driven work, type signatures are machine-checkable spec fragments — maximize where the spec is expressed as types (strict tsconfig, Sorbet srb, Dialyzer specs).
  • Deterministic, parseable output. file:line:rule diagnostics let the worker locate and self-correct. A flaky red teaches the model nothing.
  • Fast. The loop runs dozens of times per task — the underrated reason Rust-based tools (Biome, Ruff, ty) matter for agentic dev: sub-second checks change what the worker can afford per edit.

Optional typed-system enforcement (typed_enforcement, default :strict)

Enforcing typedness is distinct from running a type checker — the three levers, generalized from this platform's own typed-Elixir standard ([[typed-coding-standard]]: TypeCheck wire boundaries + Dialyzer + a hard Credo @spec gate):

  1. Strictness config — the :strict type-stage command per stack.
  2. Annotation coverage — a sub-stage that fails when public surface is untyped (the generalized @spec gate).
  3. Typed-language preference — prefer the typed variant (TS over JS, annotated Python, Sorbet-sigil Ruby); surfaced as a lint/skill expectation.

:strict is the default; :standard drops the coverage sub-stage and strict flags; :off skips the type stage entirely (quick prototypes / genuinely dynamic repos). A :strict descriptor with no strict command degrades to :standard rather than emitting a broken command.

Mutation + property testing: the layer most gates miss

LLMs excel at tests that pass and hit coverage while asserting nothing — the vacuous-test failure mode a line-coverage gate actively rewards. Mutation testing is the antidote: perturb the code, require some test to fail; if none does, the test was theater. It's the single highest-leverage addition to a spec-driven gate — run it at pre_merge/close, not per edit. Property-based tests (StreamData, Hypothesis, fast-check, proptest) are the other spec-encoding lever: assert invariants from the spec directly, which is far harder for a model to trivially satisfy than example-based tests.
