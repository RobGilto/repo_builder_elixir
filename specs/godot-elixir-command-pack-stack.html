Purpose

Answer the operator's question directly — "is there a primitive I can stack up to create command packs?" — and use it to add first-class support for a Godot game with an Elixir core. The answer is yes: the platform already has a composable primitive, and adding a stack is a small, well-bounded edit, not a new subsystem.

The primitive, in one sentence. A command pack is just a versioned folder of single-purpose command files — priv/command_packs/<pack>/<version>/commands/<name>.md — each a YAML-frontmatter .md body that may contain capability tokens ({{TEST_COMMAND}}, {{BUILD_COMMAND}}, …). You "stack up" these .md files into a pack; packs layer over a token-templated generic base through the resolver's precedence chain. You usually write only the files whose prose genuinely differs from generic.

Problem

Two real gaps stand between "the primitive exists" and "a Godot + Elixir repo just works":

  • Detection can't see the combination. Projects.Profiler scans an ordered @markers list and the first existing marker wins. A Godot + Elixir repo has both project.godot and mix.exs; because mix.exs is first, the repo is detected as plain "elixir" — the Godot half is invisible. So you cannot add this stack by simply appending one marker.
  • No capability values or pack for the combined toolchain. Projects.Capabilities.@defaults has no godot_elixir entry, and Commands.Pack.@stack_packs has no mapping, so "auto" would fall through to generic with Elixir-only (or empty) command values — nothing describes the Godot headless import/export/test flow.

Solution

Compose the existing primitive over three tiny registry edits, plus a combined-marker detection tweak. Nothing in the resolver, the Project schema, or the DB changes.

[] Phase 1: Detect the Godot + Elixir combination

Teach Profiler.detect_stack/1 to recognise a repo carrying both project.godot and mix.exs as "godot_elixir", evaluated before the ordered single-marker scan so the combination is never masked by mix.exs.

1. Add the combined-marker heuristic

  • [] In profiler.ex, wrap detect_stack/1 in a cond that checks the combination first, keeping the existing Enum.find(@markers, …) as the fallback branch: 
    defp detect_stack(root) do
  cond do
    godot_elixir?(root) ->
      %{"language" => "godot_elixir", "build_tool" => "mix+godot",
        "marker" => "project.godot+mix.exs"}

    true ->
      case Enum.find(@markers, fn {m, _l, _t} ->
             File.regular?(Path.join(root, m))
           end) do
        {marker, language, build_tool} ->
          %{"language" => language, "build_tool" => build_tool, "marker" => marker}

        nil ->
          %{"language" => "unknown", "build_tool" => nil, "marker" => nil}
      end
  end
end

@spec godot_elixir?(String.t()) :: boolean()
defp godot_elixir?(root) do
  File.regular?(Path.join(root, "project.godot")) and
    File.regular?(Path.join(root, "mix.exs"))
end

Notes

Direct answer: the two-level primitive

The operator asked whether there's "a primitive I can stack up to create command packs." There are two composable levels, and you rarely touch more than the first:

1 · The command file. A single <name>.md (frontmatter + token-templated body) under priv/command_packs/<pack>/<version>/commands/. Stack several of these into a folder and you have a pack. :-namespaced names nest (experts:ws:q → commands/experts/ws/q.md). This is the atom you "stack up."
2 · The stack wiring (3 registries). To make "auto" pick your pack for a detected repo, register the stack in Profiler.@markers (detect), Capabilities.@defaults (token values), and Pack.@stack_packs (language→pack id). That's the entire surface — the resolver, schema, and DB are untouched.

The deliberate design payoff: because the generic pack's bodies are already token-templated ({{TEST_COMMAND}} …), a brand-new stack that only supplies capability values works with zero command files. You author a pack file only when the prose truly differs — here, the Godot headless export/test flow.

Key design decision — why detection needs a heuristic, not a marker

Profiler scans an ordered list and the first existing marker wins, so appending {"project.godot", "godot", "godot"} would never fire for a Godot+Elixir repo (mix.exs precedes it) and a Godot-only marker would also steal plain-Godot repos we're not scoping here. The combined predicate (project.godot and mix.exs) evaluated first is the minimal correct change. If plain-Godot (GDScript-only) support is wanted later, add a single-marker entry after the combined check — that's a separate, additive follow-up.

Why the test pack is self-contained

The resolver precedence is repo-local → plugin → pinned → stack-pack → generic. A stack pack does not chain to the elixir pack — if godot-elixir/test.md is absent, the next layer is generic, not Elixir. So godot-elixir/test.md intentionally inlines the full Elixir green gate plus the Godot step, rather than assuming Elixir's test.md is inherited.

Capability tokens available to pack bodies

{{TEST_COMMAND}} {{BUILD_COMMAND}} {{LINT_COMMAND}} {{FORMAT_COMMAND}} {{TYPECHECK_COMMAND}} {{RUN_COMMAND}} {{PACKAGE_MANAGER}} {{SPEC_DIR}} {{SOURCE_DIRS}} {{TEST_DIR}} — filled from project.capabilities at resolve time; plus $ARGUMENTS / $1…$N for invocation args. Repo-local .claude/commands bodies are returned verbatim (no token fill) — the repo always wins.

Scope, risks, dependencies

  • No new dependency, no migration, no config. Pure code + on-disk pack files. Ship as a built-in pack under priv/command_packs/ (operator packs would instead live under config :repo_builder, :command_packs, operator_dir:).
  • Capability values are best-effort defaults. Real Godot+Elixir projects vary (NIF vs port vs sidecar). The defaults are operator-overridable per project via the changeset, so "approximately right" is acceptable; the pack prose carries the Godot specifics.
  • Out of scope: plain-Godot (GDScript-only) detection; a GUT/export ADW; per-project Godot export presets. All are clean additive follow-ups on the same three registries.
