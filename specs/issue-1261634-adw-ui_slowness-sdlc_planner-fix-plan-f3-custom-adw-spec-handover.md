# Bug: `plan_f3` step in custom ADWs produces no spec file and never hands it over to the build step

## Metadata
issue_number: `1261634`
adw_id: `ui_slowness`
issue_json: `i think we have a problem with plan_3f, i ran it on custom adws and the plan stage did not produce a spec file, the build stage did not get a hand over a spec file, it is running now ui_slowness-1261634`

## Bug Description

When an operator assembles a **custom ADW** that contains the `plan_f3` step (either via the console ADW Builder palette — the chip is exposed at `lib/repo_builder_web/components/console/adw_builder_components.ex:467` — or via the `adw_new.py` scaffolder, or via the Elixir `RepoBuilder.Adw.Scaffold` generator), the **plan stage fails silently and the build stage receives no spec file to implement**:

* Observed (live, in-flight on adw_id `ui_slowness`, issue `1261634`): the plan step completes with no spec file written to `specs/issue-1261634-adw-ui_slowness-sdlc_planner-*.{md,html}` and no `state.plan_file` recorded on `agents/ui_slowness/adw_state.json`. The chained build step then sees `spec_file = nil` and either crashes (no usable spec) or silently produces nothing because the build prompt template `Build from the plan: {{plan}}` has nothing to render.
* Expected: a `plan_f3` step is a first-class plan alternative to `plan` (`adws/adw_new.py:28`, `lib/repo_builder/adw/step_spec.ex:35`). It should invoke the HTML-first planner (`/plan_f3`, slash command registered in `SLASH_COMMAND_MODEL_MAP` at `adws/adw_modules/agent.py:53` and listed as plan-capable at `adws/adw_modules/workflow_ops.py:170`) and produce a `specs/issue-<n>-adw-<id>-sdlc_planner-*.html` artifact that the downstream `build` step picks up.

The defect is not a single line; it is three reinforcing gaps that all surface the same symptom on the `plan_f3` path while the markdown `plan` path keeps working.

## Problem Statement

Three reinforcing defects prevent `plan_f3` from working end-to-end in custom ADWs:

1. **`adws/adw_new.py` generates broken Python for the `plan_f3` (and `feature`) step blocks.** The `plan_f3_block` template at `adws/adw_new.py:48-54` emits code that (a) tries to unpack `build_plan(issue, "/plan_f3", adw_id, logger, working_dir=script_dir)` into a `(response, error)` tuple when `build_plan/5` returns an `AgentPromptResponse` (raises `TypeError: cannot unpack non-iterable AgentPromptResponse object`), (b) references an undefined `issue` variable (only `issue_number` is on the generated scope — `NameError`), and (c) references an undefined `logger` (no `setup_logger` call in the generated script — `NameError`). Any composite generated by `uv run adws/adw_new.py --steps plan_f3,…` crashes at the plan step with a Python error that is logged to the run's `events.jsonl` as `agent_call_end` `success=False` — no spec file is written, no `state.plan_file` is set, the chained build subprocess then finds no spec and aborts.

2. **`adws/adw_modules/workflow_ops.py:run_local_workflow/4` does not recognize `step == "plan_f3"`.** The step dispatcher (`adws/adw_modules/workflow_ops.py:1037-1158`) matches `step == "plan"` and falls through to `else: _local_fail(adw_id, step, f"Unknown step: {step}", logger)`. So a custom ADW launched via the **local** flavor (the `_local_iso` and `_direct` generators, or any future combo that delegates to `run_local_workflow`) with the `plan_f3` step fails immediately with "Unknown step: plan_f3" before the planner ever runs. This affects every `RepoBuilder.Adw.Scaffold`-generated `_local_iso` / `_direct` script that includes `plan_f3` (the scaffold's `render_local_iso/3` and `render_direct/3` template the step list as `STEPS = ["plan_f3", …]` and pass it straight to `run_local_workflow`).

3. **`lib/repo_builder/workflow_engine/catalog.ex:default_prompt_template/1` does not have a `plan_f3` clause.** The function falls through to the `_other` clause (`"Work on: {{input}}\n\nSpec (optional): {{spec}}"`, line 238) for `plan_f3`. So when the **console ADW Builder** assembles a workflow that includes a `plan_f3` step (palette chip at `lib/repo_builder_web/components/console/adw_builder_components.ex:467`), `launch_adw_builder/4` (`lib/repo_builder_web/live/console_live/adw_builder_panel.ex:413`) substitutes the generic "Work on: …" template as the step's `prompt_template`. The agent receiving that prompt has no instruction to author an HTML plan into `specs/`; it works the task directly and never produces a `specs/*.html` artifact. The build step's `{{plan}}` then resolves to nothing because no prior step published a `plan` artifact, and the run silently completes with no implementation.

Together: any of these paths leaves the build step with no spec to consume; the user's report ("the plan stage did not produce a spec file, the build stage did not get a hand over a spec file") is the visible surface of all three.

## Solution Statement

Surgical, three-touch fix — one per defect, no schema/DB/event-contract changes, no new dependencies:

1. **Fix `adws/adw_new.py:make_script/3`'s `plan_f3_block` (and `feature_block`) so the generated Python actually runs.** Define `issue` (synthesize via `local_ops.synthesize_issue(run)` after `local_ops.load_run(adw_id)`, mirroring the `_local_iso` pattern at `adws/adw_plan_build_local_iso.py:200-220`), define `logger` via `setup_logger(adw_id, WORKFLOW_NAME)` (same pattern as `adws/adw_plan_build_local_iso.py:323`), call `build_plan/5` correctly (it's `AgentPromptResponse`, not a tuple — check `plan_resp.success` and `plan_resp.output` instead of trying to unpack), and **persist `state.plan_file`** so the chained build subprocess finds the spec. Also persist the path to `agents/<adw_id>/run.json` `output.spec_file` (the `local_ops.update_run` call at `adws/adw_modules/workflow_ops.py:1055` shows the shape) so the orchestrator app and the ADW swimlane can display it. Use `_local_find_spec_fallback` (`adws/adw_modules/workflow_ops.py:849-857`) as the salvage path when the planner's reply is chatty (the existing `_extract_spec_path` salvage at `adws/adw_modules/workflow_ops.py:235-256` covers most cases; the fallback covers the rest).

2. **Add `step == "plan_f3"` to `run_local_workflow/4`'s dispatcher** (`adws/adw_modules/workflow_ops.py:1037`). Treat it exactly like `step == "plan"` but **force the slash command to `/plan_f3`** instead of going through `resolve_plan_command(LOCAL_ISSUE_CLASS)`. Concretely: a single shared private helper `_run_plan_step(adw_id, issue, logger, worktree_path, command)` that the existing `step == "plan"` branch calls with `command = resolve_plan_command(LOCAL_ISSUE_CLASS)` and the new `step == "plan_f3"` branch calls with `command = "/plan_f3"`. Same output-contract salvage, same `_local_find_spec_fallback`, same `state.plan_file` write, same `local_ops.update_run` for the run record. This makes every `_local_iso` / `_direct` combo with `plan_f3` work end-to-end through `run_local_workflow`, including the `RepoBuilder.Adw.Scaffold`-generated scripts.

3. **Add a `plan_f3` clause to `Catalog.default_prompt_template/1`** (`lib/repo_builder/workflow_engine/catalog.ex:220`) that returns a planf3-specific prompt template distinct from the generic `_other` fallback. The prompt must instruct the agent to author an HTML plan into `specs/issue-{n}-adw-{id}-sdlc_planner-{name}.html` per the conventions documented in `.claude/commands/plan_f3.md` (the HARD OUTPUT CONTRACT — return only the path — and the load-bearing filename) and to publish `state.plan_file` so the downstream `build` step's `{{plan}}` template resolves. Suggested template: `"Author an HTML planf3 plan into specs/issue-{issue_number}-adw-{adw_id}-sdlc_planner-{descriptive-name}.html for: {input}\\n\\nSpec (optional): {spec}\\n\\nReturn ONLY the relative plan path (Output Contract)."`. This makes the **console ADW Builder** path produce a step that actually authors a plan.

All three fixes together close the loop: an operator assembling `plan_f3 → build` through any of the three launch surfaces (console ADW Builder, `_local_iso` Scaffold, `adw_new.py` Python scaffolder) gets a real HTML plan written to `specs/`, persisted on `state.plan_file`, rendered into `{{plan}}` for the build step, and discovered by the build subprocess via the existing `_local_find_spec_fallback` glob or the in-memory `spec_file` variable.

No new dependencies (per `BUILD_PROMPT.md` §2). No DB schema or migration changes (state shape unchanged — `plan_file` is already a core `ADWStateData` field at `adws/adw_modules/data_types.py:230`). No event contract changes (the harness event contract per `BUILD_PROMPT.md` §4 is untouched). No harness adapter changes. All fixes preserve `@spec`s and the typed-Elixir standard per `BUILD_PROMPT.md` §3 (the new `Catalog.default_prompt_template/1` clause keeps the existing `@spec default_prompt_template(String.t()) :: String.t()`); Python changes follow the existing `adw_modules/workflow_ops.py` doctring conventions.

## Root Cause Analysis

The defect is the conjunction of three independent gaps that all surface the same user-visible symptom (no spec file, no build handover):

### Gap 1 — `adw_new.py:make_script/3` emits non-runnable Python for `plan_f3` and `feature`

The `plan_f3_block` literal at `adws/adw_new.py:48-54`:
```python
plan_f3_block = """    # Plan_f3: HTML-first planning into specs/ via /plan_f3 (no classify_issue).
    print(f"\\n=== PLAN_F3 PHASE ===")
    from adw_modules.workflow_ops import build_plan
    plan_resp, plan_err = build_plan(issue, "/plan_f3", adw_id, logger, working_dir=script_dir)
    if plan_err:
        sys.exit(f"plan_f3 step failed: {plan_err}")"""
```

Three correctness bugs in four lines:

* **Tuple-unpack bug.** `build_plan/5` returns `AgentPromptResponse` (declared at `adws/adw_modules/workflow_ops.py:189-238`). The generated code does `plan_resp, plan_err = build_plan(...)` which raises `TypeError: cannot unpack non-iterable AgentPromptResponse object` at runtime. The `feature_block` at `adws/adw_new.py:57-62` has the same bug.
* **Undefined `issue`.** The generated `main()` body has only `issue_number` and `adw_id` as parameters (per the script template at `adws/adw_new.py:174-181`); the `plan_f3_block` references `issue` which doesn't exist. `NameError: name 'issue' is not defined` at the planner call.
* **Undefined `logger`.** No `setup_logger` call exists in the generated script before the `plan_f3_block` is interpolated. `NameError: name 'logger' is not defined` at the planner call.

Confirmed by running `uv run adws/adw_new.py test-combo --steps plan_f3,build --local --dry-run` from `/tmp/` — the rendered output references `issue` and `logger` and unpacks `build_plan` as a tuple. Any operator who assembled a custom ADW with `--steps plan_f3,…` and ran it has seen this crash.

Even if the call succeeded, the generated code **does not persist the spec path** to `state.plan_file` — there is no `state.update(plan_file=…)` call and no `state.save(...)` call after the planner returns. So even a "successful" planner invocation would not hand the spec to the chained build subprocess (which reads `state.plan_file` from `adw_state.json` via `ADWState.load` at `adw_modules/state.py:122`). The chained build subprocess would then fail with "No plan file in state - run adw_plan_iso.py first" (`adws/adw_build_iso.py:160`).

### Gap 2 — `run_local_workflow/4` step dispatcher does not match `plan_f3`

`run_local_workflow/4` (`adws/adw_modules/workflow_ops.py:900-1183`) is the step-threading engine used by every `_local_iso` and `_direct` combo. Its main loop at line 1028+ dispatches on `step ==` against a closed set: `plan`, `build`, `patch`, `test`, `review`, `document`, `ship`. Any step name outside that set falls through to:
```python
else:
    local_ops.step_end(adw_id, step, "failed")
    _local_fail(adw_id, step, f"Unknown step: {step}", logger)
```
(`adws/adw_modules/workflow_ops.py:1158-1161`).

So when `RepoBuilder.Adw.Scaffold.render_local_iso/3` (`lib/repo_builder/adw/scaffold.ex:255-341`) emits a `STEPS = ["plan_f3", "build"]` list for a generated local-flavor combo and the script passes it to `run_local_workflow`, the run fails immediately with `Unknown step: plan_f3`. The planner is never invoked, no spec file is produced, and the run record goes to `FAILED` with `error_step = "plan_f3"`. The `:direct` flavor (`render_direct/3`, lines 350+) has the identical gap. The `:iso` flavor at `render_iso/2` (lines 100-230+) doesn't have this gap per se — it shells out to `adw_plan_f3_iso.py` — but `adws/adw_plan_f3_iso.py` does not exist in the repo (`ls adws/ | grep plan_f3` returns nothing), so the `:iso` flavor fails with `FileNotFoundError` on the subprocess, which is a different symptom but the same user-visible outcome.

### Gap 3 — `Catalog.default_prompt_template/1` has no `plan_f3` clause

`Catalog.default_prompt_template/1` (`lib/repo_builder/workflow_engine/catalog.ex:220-238`) is the single source of truth shared by `Catalog.step/4` and `ConsoleLive.launch_adw_builder/4` (`lib/repo_builder_web/live/console_live/adw_builder_panel.ex:413`) for the per-step `prompt_template` of a builder-assembled workflow. Its clauses:
```elixir
def default_prompt_template("plan"),   do: "Plan the work for: {{input}}\n\nSpec (optional): {{spec}}"
def default_prompt_template("patch"),  do: "Plan a targeted patch/hotfix for: {{input}}\n\nSpec (optional): {{spec}}"
def default_prompt_template("build"),  do: "Build from the plan: {{plan}}"
def default_prompt_template("test"),   do: "Test the implementation: {{build}}"
def default_prompt_template("review"), do: "Review the build: {{build}}"
def default_prompt_template("document"), do: "Document the implemented changes: {{build}}"
def default_prompt_template("ship"),   do: "Ship the work — finalize the branch and open a PR. Review: {{review}}"
def default_prompt_template(_other),   do: "Work on: {{input}}\n\nSpec (optional): {{spec}}"
```
There is no clause for `"plan_f3"` or `"feature"`, so a `plan_f3` step in a console-BB-built workflow gets the generic `"Work on: {{input}}\n\nSpec (optional): {{spec}}"` template. The agent receiving that prompt has no instruction to author a planf3 plan into `specs/` — the entire planf3-specific contract (filename convention, image policy, metadata header, output-contract return-only-the-path) is missing from the prompt. The agent works the task directly and never produces a spec file, so the downstream `build` step's `{{plan}}` resolves to nothing and the run silently completes with no implementation.

Note: the same fallback also affects the `"feature"` step name. The user's bug report is `plan_f3`-specific, but the fix to Gap 3 should add a `"plan_f3"` clause only — leaving `"feature"` for a separate, focused ticket — to keep this change surgical.

### Why all three gaps matter together

Each gap is independently sufficient to break the user's run on at least one launch surface:
* Gap 1 breaks the **Python-scaffolded** (`:iso` flavor) path.
* Gap 2 breaks the **Elixir-scaffolded** local / direct path (`RepoBuilder.Adw.Scaffold`).
* Gap 3 breaks the **console ADW Builder** path (workflow engine `Runner` running the harness session).

The user reports "custom ADWs" plural and an in-flight run on `ui_slowness-1261634` — the most likely cause is Gap 1 or Gap 2 (the local-flavor custom ADWs the user assembled in the console), but the fix MUST close all three to prevent the same symptom from reappearing on the next surface. Fixing only one leaves the others broken.

## Notes

- **Scope discipline**: this plan fixes the `plan_f3` path end-to-end across the three launch surfaces (Python scaffolder, `run_local_workflow`, console ADW Builder). It does NOT add an `adw_plan_f3_iso.py` script — the `:iso` flavor with `plan_f3` remains broken (would shell out to a non-existent script). That's a separate, more involved fix (requires authoring a new iso script or refactoring `run_local_workflow` to handle `isolated=True` separately from the local/direct paths). Tracked as a follow-up question in Questionables.
- **Why all three fixes are necessary**: each gap independently breaks `plan_f3` on at least one launch surface. A single-line fix would close one surface and leave the others broken; the next "custom ADW" bug report would just be about a different surface. Closing all three is still a small change set (one Python literal rewrite, one new branch, one new Elixir clause, one Runner hook) and locks the symptom at the root.
- **No DB schema or migration changes**: `state.plan_file` is already a core `ADWStateData` field at `adws/adw_modules/data_types.py:230`. `workflow_runs.output_data` is already a JSONB column with `spec_file` already documented in the `adw.run/1` schema at `adws/adw_modules/local_ops.py:38`. `workflow_runs.artifacts` is already the storage for `{{plan}}` template substitutions. The fix is purely about populating these existing fields correctly.
- **No new dependencies**: per `BUILD_PROMPT.md` §2. The Python-side fix uses only existing modules (`adw_modules.workflow_ops`, `adw_modules.state`, `adw_modules.local_ops`, `adw_modules.utils`). The Elixir-side fix adds a function clause; no new modules.
- **No event contract changes**: per `BUILD_PROMPT.md` §4. The harness event contract (canonical 8-variant Event) is unchanged; the runner hook operates on the existing `:done` event payload.
- **No harness adapter changes**: per `BUILD_PROMPT.md` §10's "adding a harness = one module + one config" doctrine, the fix doesn't add or swap a harness.
- **Why a `Runner` hook for Gap 4 and not just fix Gap 3**: the existing `{{plan}}` template variable is rendered from `workflow_runs.artifacts["plan"]` (`lib/repo_builder/workflow_engine/runner.ex:120`, `render(step.prompt_template, state.artifacts)`). Without a hook that publishes the spec path as the `plan` artifact, the build step's rendered prompt would substitute the full HTML body (huge) or fail. The hook bridges the planner's textual output to the typed `{{plan}}` template variable — same role `_local_find_spec_fallback` plays on the Python side.
- **Output-contract salvage already exists**: `adws/adw_modules/workflow_ops.py:_extract_spec_path/2` (lines 240-256) already salvages a chatty planner reply into a clean path. The Gap 2 fix reuses this unchanged. The Gap 1 fix calls `_extract_spec_path` indirectly via `build_plan` (which calls it at line 235).
- **Hardcoded `/plan_f3` in the `step == "plan_f3"` branch**: bypassing `resolve_plan_command` is intentional. The step name is the user's explicit selection of planf3; the `ADW_PLAN_COMMAND` env override is a separate, additive opt-in for users who want to override the default `plan` step's planner. Conflating them would let the env override silently nullify an explicit user selection.

The fix adds both at once because they share the same code path; deferring `feature` would leave a known-broken sibling.
- **Why no `Catalog.default_prompt_template("feature")` clause**: `feature` is the markdown `/feature` planner, which emits the spec path under the same `specs/issue-{n}-adw-{id}-sdlc_planner-{name}.md` filename convention as `plan`. The generic `"Work on: {{input}}…"` fallback is acceptable for `feature` in the console-BB path (the `_run_plan_step` dispatcher hardcoded-`/feature` invocation in Gap 2 handles the local/direct paths).
